# x86_64 machine bring-up

The x86_64 machine boots to a serial console under QEMU through PVH (Xen's para-virtualised hardware boot protocol), runs the M2 (the two-node milestone gate) mesh, and links the shared service table from `crates/kernel-core`. It has no userland and no POSIX/IRIX syscall gate, so it is not a second POSIX target yet. The Indy stays the primary machine. No wire format, ABI or service gains an x86 variant. Terms used on this page are collected in the [glossary](../introduction/glossary.md).

Tracking: [irix7/os#266](https://github.com/irix7/os/issues/266).

## Why a second machine type

The Indy is the product target. Eight real Indys are the practical ceiling for hardware-in-the-loop testing. A supported QEMU x86_64 machine gives CI a fast, deterministic target for the same kernel contract, and it exercises the machine abstraction on a second real machine. The scale plan is [irix7/os#267](https://github.com/irix7/os/issues/267).

## Boot path

The image is an ELF64 kernel linked at 1 MiB with a Xen PVH entry note (`XEN_ELFNOTE_PHYS32_ENTRY`, type 18). QEMU's `-kernel` option recognises the note, loads the ELF and starts the named 32-bit entry with `%ebx` holding the physical address of `hvm_start_info`.

PVH was chosen over Multiboot2 and UEFI for this slice for three reasons. rustc emits ELF64 and QEMU's multiboot loader expects 32-bit ELF. PVH is a documented boot ABI that QEMU implements directly, so the CI path needs no external bootloader, no 32-bit image and no firmware. PVH exists only under a hypervisor, so UEFI remains the entry for real hardware and is Phase 6 of the milestone plan. The machine layer above the stub does not depend on which entry protocol started it.

1. `_start32` (`kernel-x86/src/boot.S`) zeroes `.bss`, saves the start-info pointer, builds an identity map of the first 4 GiB with 2 MiB pages, enables PAE, long mode and paging, and far-jumps to 64-bit code.
2. `start64` loads a flat data selector and calls `kernel_main`.
3. `kernel_main` brings up COM1, reads the PVH memory map, installs the IDT (interrupt descriptor table), remaps the 8259 PIC (interrupt controller), starts the 8254 PIT (interval timer) at 100 Hz, and waits for ten ticks.
4. It then executes `int3`. The handler reports the vector, error code and faulting instruction pointer, prints `x86: halted`, and leaves QEMU through `isa-debug-exit`.

The identity map covers 4 GiB because the UART, the PIC and later the PCI base-address registers live below that line. The frame allocator can hand out any page in the window. The machine layer narrows the mapping once the shared core owns it.

## Device set in this slice

| Device | Use | Address |
|---|---|---|
| 16550 UART (COM1) | boot console, polled | `0x3F8` |
| 8259 PIC | IRQ0 remapped to vector 32 | `0x20`, `0xA0` |
| 8254 PIT | 100 Hz tick | `0x40`, `0x43` |
| `isa-debug-exit` | clean QEMU exit for the gate | `0x501` |

The PVH memory map replaces hardware probing. The machine reads the DRAM geometry the loader reports; the Indy ROM sizes its banks by probing. Reserved holes stay reserved.

## What this slice does not do

- It does not run a userland or a native syscall gate. The shared core covers the service ABI. The fd table, ramfs, thread table and native syscalls are still MIPS-only and need the process model in [irix7/os#326](https://github.com/irix7/os/issues/326) before they can move.
- The heap is a bump allocator with no reclamation.
- There is no SMP, no IO-APIC, no PCI enumeration and no ACPI.
- There is no paging API beyond the identity map, and no interrupt-driven serial input.
- The Indy boot and M2 two-node gates are unchanged and remain the product gates.

## Building and running

```sh
export PATH="$HOME/.cargo/bin:$PATH"   # pinned nightly with rust-src + llvm-tools
tools/x86-qemu.sh                      # builds and boots under QEMU
```

The script builds `kernel-x86` for `x86_64-unknown-none` with `-Zbuild-std=core`, boots it under `qemu-system-x86_64 -M q35`, checks the serial markers and the usable-RAM total, and requires QEMU to exit with status 1. The guest calls `qemu_exit(0)` through `isa-debug-exit`, which encodes the guest value as `(value << 1) | 1`. A hang ends at the script's timeout.

CI runs the same script in the **Boot (x86_64 QEMU)** job.

## Release artefact

`scripts/release/build.sh` publishes `irix7-x86_64.elf` alongside the Indy `irix7-rom.bin` and the signed runtime graph. `manifest.json` is keyed by machine:

```json
"machines": {
  "indy": { "arch": "mips3", "kernel_abi": "n32", "rom_abi": "o32", ... },
  "x86_64": { "arch": "x86_64", "image": "irix7-x86_64.elf", "stage": "boot" }
}
```

`stage: boot` records that the x86 image is not an M2 node yet. The manifest must not imply otherwise.

## Memory and heap (second slice)

The physical frame allocator is the shared `crates/frame-alloc` crate, which the Indy kernel also uses. The machine supplies the descriptor list and the reference-count array; the kernel's own statics hold them.

- The PVH memory map becomes `MemDesc`s. Type 1 is usable RAM and everything else is reserved.
- The low megabyte and the whole kernel image are reserved, including `.bss`, the boot stack and page tables. `__kernel_end` in `linker.ld` marks the end.
- The allocator tracks 1 GiB of frames. Frames above that are never handed out.
- A 1 MiB bump heap is taken from the frames and installed as the global allocator. It never reclaims memory; a free-list allocator is the next step.

The gate checks the frame count, a frame allocated above the heap, and a 1000-element `Vec` summing to 499500.

## Network (third slice)

The machine finds a legacy virtio-net device on bus 0 through the PCI configuration ports and drives it through its I/O-port register block. The driver is polled: no device interrupt is enabled. The stack is the same smoltcp setup the Indy kernel runs, with DHCP for the address.

- The gate runs QEMU with `-netdev user -device virtio-net-pci,disable-modern=on`. `disable-modern` keeps the driver on the legacy interface, which needs only port I/O and no PCI capability walk.
- The gate checks the MAC, the DHCP address `10.0.2.15` and the gateway `10.0.2.2`.
- Not yet: interrupts, multiple queues, bridges on the PCI bus, and the `virtio-blk` device.

## Block (fourth slice)

`virtio-blk` runs on the same legacy transport (`kernel-x86/src/virtio.rs`), polled, one request at a time. A request is three chained descriptors: a header, a 512-byte data buffer and a status byte. The gate builds a 2 MiB raw disk with a marker in sector 1, then checks that the marker reads back and that a written sector reads back unchanged. The virtio ring code is shared by the network and block drivers.

Not yet: multi-sector requests, flush, and the epoch store on top of the disk.

## Module services on x86 (ninth slice)

This slice is recorded as history: the kernel no longer has a module loader (ADR M1-0003 step 6). `config_get` read `key=value` lines from disk sectors 100-103. The block service served module target 3 from a reserved region at sector 4096, so the mesh epoch store had a place that did not overlap the boot header or the configuration. Both used the shared `irix7-config` and `block-store` crates; the Indy's block service used the same crate with targets passed through to SCSI.

Still refused at the time: UDP, console input, screen, module-to-module arena services.

## Module load (fifth slice)

This slice is recorded as history: the kernel no longer has a module loader (ADR M1-0003 step 6). The MCP (Model Context Protocol control plane) module loaded, its SHA-256 was checked, and its entry returned status 0 on the x86 machine. [`x86-module-slice.md`](x86-module-slice.md) records the layout, the service table and what was missing.

## Shared code between the kernels

Code that does not depend on the machine lives in a crate under `crates/`, and both kernels depend on it. A kernel keeps only what is specific to its hardware.

| Crate | What it holds | Used by |
|---|---|---|
| `frame-alloc` | Physical frame allocator and its fixed-capacity `Store` | Indy, x86 |
| `irix7-sha256` | SHA-256 and digest hex parsing | Indy, x86 |
| `irix7-fmt` | Decimal, hex and dotted-quad output through a byte sink | Indy, x86 |
| `irix7-netif` | Applying a DHCP lease to the interface | Indy, x86 |
| `tcp-slots` | The module TCP slot table, over a `Stack` trait | Indy, x86 |
| `irix7-config` | `key=value` boot configuration lookup | Indy, x86 |
| `block-store` | The module block service, over a `Block` trait and a `Store` policy | Indy, x86, PowerPC |
| `kernel-core` | Module header, digest, vtable and entry rules; the one module service table and its platform boundary | Indy, x86, PowerPC |

The table records the split at the time of the module slices. The module header, digest and entry rules left `kernel-core` with the module loader (ADR M1-0003 step 6); the service table remains. Each kernel implements what the crates need from its machine: the serial sink, the smoltcp stack accessors, the memory map and the cache maintenance.

Three things stay machine-specific on purpose.

- **NIC device tokens.** The Indy's Seeq device hands smoltcp descriptor slots directly; the x86 virtio driver copies frames. Converting the Indy to a copy path changes its timing, and the two-node gate is timing-sensitive.
- **HTTP clients.** The Indy's client drives its own sockets and handles ranges and redirects. The x86 fetch drives a TCP slot and handles one GET. Sharing them needs a transport trait; that is a separate change.
- **Module transports and windows.** During the module slices the Indy had two fixed slots and a SCSI or HTTPS fetch, the x86 machine had two 2 MiB windows and an HTTP fetch, and the PowerPC machine streamed from ATA. `kernel-core` owned the rules that decided whether an image could run; the machine owned how its bytes arrived and where the window was.
