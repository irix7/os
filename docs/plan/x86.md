# x86_64 machine bring-up

**Issue:** [#266](https://github.com/irix7/os/issues/266)
**Status:** first slice. The machine boots to serial with a loader-provided memory
map, traps and a timer; the shared kernel core is not linked in yet.

This document records the x86_64 machine's boot path, the boundary it is being
built behind, and the limits of the current slice. It is not a compatibility
layer: the Indy remains the primary machine, and no wire format, ABI or service
gains an x86 variant.

## Why a second machine type

The Indy is the product target, but eight real nodes are the practical ceiling
for hardware-in-the-loop testing. A supported QEMU x86_64 machine gives CI a
fast, deterministic target for the same kernel contract, and it exercises the
machine abstraction for real rather than through a mock. The scale plan is
[#267](https://github.com/irix7/os/issues/267).

## Boot path

The image is an ELF64 kernel linked at 1 MiB with a Xen PVH entry note
(`XEN_ELFNOTE_PHYS32_ENTRY`, type 18). QEMU's `-kernel` recognises the note,
loads the ELF and starts the named 32-bit entry with `%ebx` holding the
physical address of `hvm_start_info`.

**Why PVH rather than Multiboot2 or UEFI in this slice:** rustc emits ELF64,
QEMU's multiboot loader is 32-bit-ELF oriented, and PVH is a documented boot
ABI that QEMU implements directly — no external bootloader, no 32-bit image and
no firmware dependency in the CI path. PVH only exists under a hypervisor, so
UEFI remains the real-hardware entry and Phase 6 of the milestone plan; the
machine layer above the stub does not depend on which entry protocol got it
there.

1. `_start32` (`kernel-x86/src/boot.S`) zeroes `.bss`, saves the start-info
   pointer, builds an identity map of the first 4 GiB with 2 MiB pages, enables
   PAE, long mode and paging, and far-jumps to 64-bit code.
2. `start64` loads a flat data selector and calls `kernel_main`.
3. `kernel_main` brings up COM1, reads the PVH memory map, installs the IDT,
   remaps the 8259 PIC, starts the 8254 PIT at 100 Hz, and waits for ten ticks.
4. It then executes `int3`. The handler reports the vector, error code and
   faulting instruction pointer, prints `x86: halted`, and leaves QEMU through
   `isa-debug-exit`.

The 4 GiB identity map is deliberate: the UART, the PIC and later PCI base-address registers live
below it, and the frame allocator can hand out any page in that window until
the machine layer narrows the mapping once the shared core owns it.

## Device set in this slice

| Device | Use | Address |
|---|---|---|
| 16550 UART (COM1) | boot console, polled | `0x3F8` |
| 8259 PIC | IRQ0 remapped to vector 32 | `0x20`, `0xA0` |
| 8254 PIT | 100 Hz tick | `0x40`, `0x43` |
| `isa-debug-exit` | clean QEMU exit for the gate | `0x501` |

The PVH memory map replaces hardware probing: the machine reads the DRAM
geometry the loader reports rather than sizing banks the way the Indy ROM does.
Reserved holes stay reserved.

## What this slice does not do

- It does not link the shared kernel core. `kernel-x86` is the seed of the
  machine layer; the next slice moves the core onto it rather than copying
  kernel logic.
- The heap is a bump allocator with no reclamation. There is no module slot or module loader on x86 yet.
- There is no virtio-net or virtio-blk, so no mesh, module fetch or M2 gate.
- There is no SMP, no IO-APIC, no PCI enumeration and no ACPI.
- There is no userland, no paging API beyond the identity map, and no
  interrupt-driven serial input.
- The Indy boot, M2 two-node and module-transport gates are unchanged and
  remain the product gates.

## Building and running

```sh
export PATH="$HOME/.cargo/bin:$PATH"   # pinned nightly with rust-src + llvm-tools
tools/x86-qemu.sh                      # builds and boots under QEMU
```

The script builds `kernel-x86` for `x86_64-unknown-none` with
`-Zbuild-std=core`, boots it under `qemu-system-x86_64 -M q35`, checks the
serial markers and the usable-RAM total, and requires QEMU to exit with status
1 (`qemu_exit(0)` through `isa-debug-exit`, which encodes the guest value as
`(value << 1) | 1`). A hang surfaces as the timeout, not as a stalled job.

CI runs the same script in the **Boot (x86_64 QEMU)** job.

## Release artefact

`scripts/release/build.sh` publishes `irix7-x86_64.elf` alongside the Indy
`irix7-rom.bin` and the signed runtime graph. `manifest.json` is keyed by
machine:

```json
"machines": {
  "indy": { "arch": "mips3", "kernel_abi": "n32", "rom_abi": "o32", ... },
  "x86_64": { "arch": "x86_64", "image": "irix7-x86_64.elf", "stage": "boot" }
}
```

`stage: boot` is deliberate: the x86 image is not an M2 node yet, and the
manifest must not imply otherwise.

## Memory and heap (second slice)

The physical frame allocator is the shared `crates/frame-alloc` crate, which
the Indy kernel also uses. The machine supplies the descriptor list and the
reference-count array; the kernel's own statics hold them.

- The PVH memory map becomes `MemDesc`s. Type 1 is usable RAM and everything
  else is reserved.
- The low megabyte and the whole kernel image are reserved, including `.bss`,
  the boot stack and page tables. `__kernel_end` in `linker.ld` marks the end.
- The allocator tracks 1 GiB of frames. Frames above that are never handed out.
- A 1 MiB bump heap is taken from the frames and installed as the global
  allocator. It never reclaims memory; a free-list allocator is the next step.

The gate checks the frame count, a frame allocated above the heap, and a
1000-element `Vec` summing to 499500.
